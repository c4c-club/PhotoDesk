## 0. 结论摘要

4. 建议 **9 个阶段（Phase 0–8）**，约 **18–23 个开发日**（新增 D16 的会话/补位/持久化与 D17 的发布链路）。每个阶段都必须有可自动化的验收，不靠"目测没问题"。

### D01 · 查看大图永远显示最新一张

**现象**：点网格中任意一张，进入全屏后总是第 1 张（最新）。

**根因链**：

1. `PhotoDesk/Features/Viewer/ViewerViewController.swift:114-118`
   `setupCollectionView()` 在 `viewDidLoad` 里调用 `collectionView.scrollToItem(...)`。此时 collection view 尚未完成首次布局，`itemSize` / contentSize 还未建立，该调用不会真正滚动。
2. `ViewerViewController.swift:690-699`
   初次布局后 contentOffset 仍为 0，`scrollViewDidScroll` 把 `page = 0` 写回 `viewModel.updateIndex(0)`，**覆盖了 init 时传入的 `startIndex`**。
3. `PhotoDesk/Features/Library/LibraryViewController.swift:479-485`
   传给查看器的是"按 section 累加的扁平 index"；而查看器的 `items` 来自 `LibraryViewModel.itemsSnapshot`（已加载条目）。只要分组顺序、筛选结果或加载数量与网格不一致，index 就会错位。
4. `PhotoDesk/App/AppContainer.swift:32-39`
   `makeViewerViewModel(startIndex:)` 只接受 Int，没有任何"按 assetID 定位"的能力；任何列表变化都会让旧 index 失效。

**修复策略**：

- 新增 `ViewerContext`：`items: [PhotoItem]` + `startItemID: String` + `queryKey: String`，由网格点击时直接传当前筛选结果与点击的 `PhotoItem.id`。
- `ViewerViewController` 增加 `pendingInitialItemID`；在 `viewDidLayoutSubviews` 首次拿到有效宽度后 `setContentOffset(x: index * width, animated: false)`，并显式 `viewModel.updateIndex(index)`。
- `scrollViewDidScroll` 只在 `scrollView.isTracking || scrollView.isDecelerating` 时更新 index；程序化滚动由 `isProgrammaticScroll` 标志屏蔽。
- 所有"翻页/自动前进/删除后定位"统一走 `scrollToItemID(_:)`，不再用裸 index 跨层传递。

**验收**：UI 测试点击第 8 张 → 查看器 DEBUG 横幅显示 `id=<第8张的 assetID>`；左右各滑一次仍与网格顺序一致。

### D02 · 图片显示错误导致删错图片

**现象**：大图显示的和被删除的不是同一张；删除后下一张错位；有时出现上一张的图。

**根因链（四个独立缺陷叠加）**：

1. **删除后集合视图不同步（最致命）**
   `ViewerViewModel.swift:177-183` 的 `removeLocally(_:)` 只修改 `items` 数组，没有通知 `ViewerViewController` 的 `UICollectionView`。`numberOfItems` 变了，但 cell 没删、contentOffset 没改。此时 `currentIndex` 仍指向同一格，而 `items[currentIndex]` 已经换成下一张照片——屏幕还显示被删的那张，下一次删除却删掉下一张。
2. **加载 token 按 index 而非 cell+assetID**
   `ViewerViewController.swift:613-630` 的 `loadTokens[index]` 只防"同一 index 的旧请求"，不防"cell 被复用给另一个 index"。旧请求完成后 token 仍然匹配，把上一张图写进已经显示新照片的 cell。
3. **复用不清图**
   `ZoomableImageCell.swift:148-158` 的 `configure(item:image:)` 在 `image == nil` 时不清空 `imageView.image`；cell 复用瞬间会显示上一张，直到新图回来。
4. **执行期间目标漂移**
   `ViewerViewController.swift:388-415` 的 `perform(action:for:)` 在 `await` 前取 `viewModel.current`，`await` 后 `flyOut` 又用 `viewModel.currentIndex` 取 cell。PhotoKit 写操作期间用户可能翻页、observer 可能插入/删除，导致动画和删除目标不是同一张。

**修复策略**：

- `ViewerViewController` 持有 `displayedItems` 镜像；VM 的删除/隐藏返回 `StagedAction(removedIndex, plan)`，VC 执行：
  ```swift
  collectionView.performBatchUpdates {
      collectionView.deleteItems(at: [IndexPath(item: removedIndex, section: 0)])
  } completion: { _ in
      self.applyReplacement(plan)   // snapshot 从 entryEdge 进入
  }
  ```
  同时更新 `filmStrip` 的 ids 与高亮。
- `execute(_:forItemID:)`：进入时解析并冻结 `itemID`；收藏/取消收藏等仍需 await 的写操作只认这个 id，await 后重新按 id 查 index，查不到就只刷新不动画；删除/隐藏走同步入队，不 await。
- `loadImage(for:at:cell:)` 改为 cell 级 token：`cell.beginLoad(assetID:) -> token`；回填前 `guard cell.itemID == item.id, cell.loadToken == token`。
- `ZoomableImageCell.configure` 在设置新 item 时 `imageView.image = nil`、`resetZoom()`、取消旧任务。
- 删除/隐藏改为 **会话暂存（D16）**：滑动只入队并本地移除，**不等待 PhotoKit 写操作**；`execute` 返回 `.staged(replacement:)`，VC 立即做飞出动画和补位，不再有 await 后 target 漂移。
- 删除后自动前进/补位策略由 `PhotoDeskCore.ReplacementPlanner` 决定（见 D16）：
  - 删除/隐藏：item 从当前整理队列移除，**保持当前 index**（原位置变成下一张）；若已是最后一张则回退一张；列表空则关闭查看器。
  - 补位方向：上滑删除 → 下一张从**底部**补位；下滑删除 → 下一张从**顶部**补位；到末尾回退时，上一张从**与飞出方向相同**的一侧补位；工具栏删除无手势 → 默认从底部补位。
  - 收藏/取消收藏/加相簿/分享/信息：不前进。
  - 旧代码 `nextIndexAfterAction = currentIndex + 1` 在删除后会跳掉一张，必须删除该逻辑。
- 补位动画用 `UIViewPropertyAnimator` + `snapshotView`：当前 cell 飞出，下一张从计算出的边缘以 0.96→1.0 缩放进入；动画期间禁止重复手势，动画结束再解锁。
- 预取下一张/下三张（`UICollectionViewDataSourcePrefetching` + `ImagePipeline`），保证补位时图片已解码，不出现白屏或旧图。

**验收**：连续删除 3 张，逐张比对 DEBUG 横幅的 assetID 与删除前一致；删除后左滑/右滑不出现跳图；无 cell 显示上一张。

### D03 · 删除时系统提示"是否允许照片管家删除"

**平台事实（2026-11-03 核实，结论不可绕过）**：

- 删除的唯一合法实现是 `PHAssetChangeRequest.deleteAssets`（`PhotoDesk/Core/Photos/PhotoWriter.swift:70-76`）。
- iOS 对 `deleteAssets` **必然弹出系统级确认框**，文案与按钮由系统控制，**公共 API 无法关闭、无法自定义、无法预授权**。Apple Developer Forums 的删除 API 讨论也明确写着 "The system should present a confirmation dialog"；Stack Overflow 的结论是 "I cannot see a way to avoid the delete confirmation"。
- 市面上的照片清理 App **没有绕过系统确认**：
  - Swipewipe 官方 FAQ 明确写："Swiping left only marks a photo. The marked photos are deleted when you confirm on the review screen."
  - Swipewipe 官网写："Nothing is deleted until you confirm. Swiping left marks a photo for deletion."
  - Slider 的 [App Store 评论](https://apps.apple.com/us/app/photo-video-cleaner-slider/id6444738335)仍能看到 "Allow Slider to delete this photo?" 的系统确认。
  - 系统「照片」App 能直接删除，是因为它是系统级 App，拥有第三方无法使用的私有能力；第三方不能复制。
- 因此，**当前"每张都弹"的真正根因不是 App 的二次确认，而是每滑一张就调用一次 `deleteAssets`**：每次 `performChanges` 都会触发一次系统确认。100 张就是 100 次系统弹窗，产品当然不可用。

**当前代码为什么每张都弹**：

1. `ViewerViewModel.swift:109-143` 的 `moveToRecentlyDeleted` 在每次滑动时调用 `writer.moveToRecentlyDeleted(ids: [item.id])`。
2. `PhotoWriter.swift:70-76` 每次调用都执行一次 `PHPhotoLibrary.performChanges { PHAssetChangeRequest.deleteAssets(...) }`。
3. 每次 `performChanges` 都触发一次系统确认框；`perform` 还会等这个系统确认结束后才 `flyOut`，所以滑动被系统弹窗打断，完全无法形成连续操作。

**方案：会话暂存 + 一次性批量提交（推荐，也是本次采用方案）**：

1. **滑动时不写 PhotoKit**。下滑/上滑触发删除时，只做三件事：
   - `ReviewSession.markDelete(assetID)` 记录到内存队列；
   - 从当前整理队列本地移除该 item，下一张立即补位；
   - 写入 `PendingActionStore`（JSON，防杀进程丢失）。
2. **不在滑动过程中调用 `deleteAssets`**，也不调用 `TrashBin.storeCopy`（副本留到提交时统一做）。
3. 顶部显示「待删除 N」；点「完成整理」进入 `SessionReviewView`，列出待删除缩略图，可逐张恢复、继续整理、或「全部移到最近删除」。
4. 用户点「全部移到最近删除」时，才调用**一次** `PHAssetChangeRequest.deleteAssets`，传入所有待删除 assetID。系统确认只出现**一次**（单批上限内；超过上限按批，每批一次，不是每张）。
5. 用户在系统确认框点取消：队列保留，不丢数据；返回可继续整理或再次提交。
6. App 自己的删除二次确认全部移除：`presentConfirmation` 的删除分支、`LibraryViewController.batchDeleteTapped` 的 alert、`CleanupView` 的 confirmationDialog 删除确认全部删除；**不保留 `confirmDestructive`/`confirmDeleteInApp` 设置开关**（用户明确要求不再出现 App 删除确认）；`SwipeGestureEngine.config(for:confirmDestructive:)` 的 `confirmRequired` 固定 false 或移除该参数。
7. 代码门禁：全仓库只允许 `PhotoWriter.moveToRecentlyDeleted` 内部出现 `PHAssetChangeRequest.deleteAssets`；其他任何文件出现即失败。

**"全程零系统弹窗"的可行性**：

- **做不到**，除非改变产品定义。只有三条路：
  1. **一次批量提交**（本方案）：滑动全程 0 弹窗，最后提交时 1 次系统确认；这是公共 API 下最接近"无感"的方案。
  2. **只隐藏、不真删**：`isHidden = true`，通常无系统确认，但**不释放存储空间**，照片仍在系统「已隐藏」。
  3. **私有 API / 系统 entitlement / 非 PhotoKit 删除**：违反红线与 App Store 规则，明确禁止。
- 如果用户要求"连最后这一次系统确认也不能有"，只能在产品上选择第 2 条（仅隐藏）或接受"不真正删除"；这需要改产品定义，不能靠代码绕过。

**竞品参考（供产品确认）**：

- [Swipewipe Help](https://swipewipe.com/help)：swipe 只标记，review screen 确认后才删除。
- [Swipewipe 官网](https://swipewipe.com/)："Nothing is deleted until you confirm."
- [Stack Overflow: Disable confirmation on delete request in PHPhotoLibrary](https://stackoverflow.com/questions/31922796/disable-confirmation-on-delete-request-in-phphotolibrary)：公共 API 无法关闭。
- [Apple Developer Forums: deleteAssets confirmation](https://developer.apple.com/forums/thread/806349)：系统应显示确认框。

**验收**：

- 连续下滑 20 张：全程 **0 次系统弹窗**，顶部计数 20，画面连续补位。
- 点「全部移到最近删除」：**恰好 1 次**系统确认；确认后 20 张进入系统「最近删除」。
- 在系统确认框点取消：20 张仍在待删除队列，App 不丢数据。
- 杀 App 重启：待删除队列恢复，不自动弹系统框。
- 全仓库 `grep deleteAssets` 只出现在 `PhotoWriter.moveToRecentlyDeleted`。

> **给用户的实话**：如果"去除这个提示"指的是连最后批量提交的 1 次也不要，那么在"删除必须进系统最近删除"的前提下**做不到**。本方案解决的是"每张都弹、根本无法连续操作"这个真正的痛点；最后 1 次是 iOS 的安全边界，不是 App 的 bug。

### D04 · 隐藏时提示"是否允许照片管家隐藏"

**根因**：从代码看，当前至少有一个 App 自己的确认框：
`PhotoDesk/Core/Support/SettingsStore.swift:54-60` 把 `.hide` 标成 `isDestructive = true`；`SettingsStore.swift:75` 的 `gesture.confirmDestructive` 默认 `true`；`ViewerViewController.swift:359-360` 因此对隐藏也弹 `presentConfirmation`。
另外，当前隐藏是每张一次 `writer.setHidden(ids: [item.id])`，即使没有系统弹窗，也会让每张都等待一次 PhotoKit 写操作，破坏连续滑动。

**弹窗归属**：`isHidden = true` 是公开 API，Apple 文档没有要求系统确认；从代码看当前提示是 App 自己的 `UIAlertController`。**执行时仍要在真机确认**：如果真机出现系统对 `isHidden` 的确认，则与 D03 同属平台限制，采用"批量隐藏一次确认"，不要尝试绕过。

**方案：与删除共用 `ReviewSession`，但隐藏走独立批量队列**：

- `ReviewSession` 同时维护 `pendingDelete` 与 `pendingHide` 两个集合；滑动隐藏只入队、做本地移除、立即补位，**不等待 PhotoKit**。
- `PendingHideQueue` 在以下时机统一提交（一次 `performChanges` 批量 `isHidden = true`）：
  - 用户点「完成整理」/离开整理会话；
  - 进入「已隐藏」页之前；
  - App 进入后台之前；
  - 队列达到 500 张时（仍是一次批量写）。
- 隐藏队列提交前，`VaultViewModel` 通过 `pendingHideIDs` 把待隐藏资源也合并进隐藏列表，显示「待隐藏」角标；用户可在 Vault 里取消隐藏（直接从队列移除，不写库）。
- 隐藏不弹 App 确认；如果真机确认 `isHidden` 有系统确认，则同样只在批量提交时出现一次，不是每张一次。
- 取消隐藏（unhide）立即写库并本地移除；若失败，恢复 item 并 Toast。
- 隐藏**不等于删除**，不释放存储空间；文案必须写清楚「已隐藏到系统「已隐藏」相册」。

**验收**：

- 连续下滑隐藏 20 张：0 次 App 弹窗；画面连续补位；顶部「待隐藏 20」。
- 进入「已隐藏」：能看到这 20 张（合并 pending）；全部取消隐藏后列表恢复为空。
- 结束会话/进入 Vault 时只发生一次批量 `performChanges`（代码日志可证）；系统「已隐藏」相册可见。
- 若真机出现系统确认，只出现一次（批量），不是 20 次；记录为平台事实。

### D05 · 隐藏照片在 App 内无法查看

**根因（四个）**：

1. `PhotoDesk/Features/Vault/VaultView.swift:19-29`：只有点击"使用 Face ID / 密码解锁"按钮才调用 `loadHidden()`。如果 `vaultLockEnabled == false`，或 5 分钟宽限期内 `vault.isUnlocked == true`，直接进入 `gridView`，**`loadHidden()` 永远不会执行** → 永远空列表。

- 新增 `VaultViewModel`（`@MainActor`）：

  - `func load() async`：先 `reviewSession.flushHidesIfNeeded(reason: .enterVault)`（待隐藏提交），再 `repository.prepare(scope: .hidden)` → 分批 500 取全量；合并 `reviewSession.pendingHideIDs`（尚未提交的隐藏项）；注册 `PhotoChangeObserver`（`.hidden` scope）增量刷新。

- `VaultView` 重构：
  - `.task { await viewModel.onAppear() }`：如果锁定则自动唤起 Face ID；如果已解锁/关闭锁则直接 `load()`。
  - 网格 cell 可点击 → 以 `ViewerContext(items: hiddenItems, startItemID: id)` 打开同一套 `ViewerContainer`。网格必须用 UIKit `UICollectionView`（复用 `PhotoGridCell`），不要用 SwiftUI `LazyVGrid`；隐藏库量级小不是违反 AGENTS §3.3 的理由。
  - 长按/上下文菜单：取消隐藏、移到最近删除、收藏、在系统相册中查看。

  - 失败态：显示具体原因 + 「重试」+「去系统设置」；`limited` 权限时提示"受限访问下无法读取已隐藏照片，请允许完全访问"。
  - 离开页面 `vault.lock()`；后台时加隐私遮罩。
- 主查看器：隐藏成功后按 D02 的移除逻辑从 `items` 删除该 id，并关闭/前进，避免残留。

### D07 · 存储统计一直转圈

**根因**：`PhotoDesk/Features/Export/StorageStatsView.swift:216-269`

1. 用 `withTaskGroup` 为**每一张照片**创建一个子任务，每个子任务内部再 `PHAsset.fetchAssets(withLocalIdentifiers:)` 查一次。
2. 5,300 张就是 5,300 次 PhotoKit 查询 + 5,300 次 `PHAssetResource.assetResources` + 私有 KVC `fileSize`；万级库会达到数万次查询，耗时从"很久"退化到"看起来永远"。
3. `compute()` 没有进度、没有取消、没有超时；`isLoading` 只在成功末尾置 false，异常/挂起时永远转圈。
4. `@MainActor` 上启动大量子任务，主线程被 `await` 之外的工作挤占。
5. `PHAsset+FileSize.swift` 的 KVC 对 iCloud-only 可能返回 0，统计会显示 0 但用户不知道"未知"。

**修复策略**：

- 新增 `AssetSizeProviding` 协议与 `PhotoKitAssetSizeProvider`：
  ```swift
  protocol AssetSizeProviding {
      func sizes(for ids: [String], progress: @escaping (Int, Int) -> Void) async -> [String: Int64]
  }
  ```
  - **批量取**：每 500 个 id 一次 `PHAsset.fetchAssets(withLocalIdentifiers:)`，再在 `Task.detached(priority: .utility)` 里枚举 `PHAssetResource`。
  - 并发上限 4（`AsyncSemaphore` 或 `TaskGroup(maxConcurrent:)`），不要每张一个任务。
  - 每批回调进度；`Task.checkCancellation()`。
- 新增 `StorageStatsService`（纯聚合，可单测）+ `StorageStatsViewModel`（`@Published phase/progress/stats`）。
- 新增 `AssetSizeCache`（`Application Support/AssetSizeCache.json`，按 `assetID + modificationDate` 缓存 `bytes`）：命中缓存直接复用；`modificationDate` 变了才重算；写入节流；设置页「清理统计缓存」。**不要给 Core Data 加实体**——现有 `PersistenceController` 是程序化模型且未启用自动迁移，新增实体会让老用户 store 加载失败。
- UI：
  - 统计中显示环形进度 + `已统计 N / M` + 「取消」。
  - 90 秒软超时：显示已完成部分 + "部分 iCloud 资源大小未知" + 「继续统计」；不再无限转圈。
  - 完成后显示总占用、类型环、年份柱；`unknownCount > 0` 时显示脚注。
  - `.refreshable` 强制重算。
- 单元测试用 mock provider 验证聚合/进度/取消；UI 测试用 `-uiTestingStorageMock` 注入固定数据，断言 5 秒内出结果。

**验收**：5,300 张库 30 秒内出首屏（可先显示已统计部分），最终完成 < 90 秒；取消立即停止；再次进入命中缓存 < 1 秒；无"永久转圈"。

### D09 · 隐藏、删除应进入系统隐藏 / 最近删除空间

**现状判断**：核心写入语义**已经正确**：

- 隐藏：`PhotoWriter.setHidden` → `PHAssetChangeRequest.isHidden = true` → 系统「已隐藏」。
- 删除：`PhotoWriter.moveToRecentlyDeleted` → `PHAssetChangeRequest.deleteAssets` → 系统「最近删除」。

**但链路有 5 个缺陷，导致用户感知"没进系统相册"**：

1. `VaultView` 不自动加载（D05）→ 用户看不到隐藏结果。
2. `VaultView` 无 observer → 隐藏/取消隐藏后不刷新。
3. `LibraryViewModel.performBatch(.moveToRecentlyDeleted)`（`LibraryViewModel.swift:167-188`）**无条件** `trashBin.storeCopy`，忽略 `settings.safetyCopyEnabled`；开关关闭时仍会产生副本，行为与设置不一致。
4. 查看器隐藏后不把自己从 `items` 移除（D02 同源），用户还能在查看器里看到已隐藏照片。
5. 批量删除后没有明确文案告诉用户"已进入系统最近删除"。

**修复策略**：

- 保持 `isHidden` / `deleteAssets` 不变；不新增任何"永久删除"路径。
- 所有删除/隐藏先进入 `ReviewSession`（D16）；只有 `BatchCommitCoordinator` 能调用 `PhotoWriter`：
  - 删除：一次 `deleteAssets` 提交全部待删除 id；`if trashBin.isSafetyCopyEnabled { storeCopy }` 在提交前统一做；副本关闭时直接删除，`undoKind = nil`。
  - 隐藏：一次 `setHidden(ids:isHidden:true)` 提交全部待隐藏 id。
- 隐藏/删除成功 Toast 统一为：
  - 「已隐藏到系统「已隐藏」相册 · 撤销」
  - 「已移到系统「最近删除」· 撤销」（无副本时后缀「· 可在系统相册恢复」）
- `VaultView` + `LibraryViewModel` 注册 observer，写后刷新；Vault 同时合并 `ReviewSession.pendingHideIDs`，展示「待隐藏」。
- `RecentlyDeletedView` 保持说明 + `photos-redirect://` 跳转（iOS 无公开 API 枚举最近删除，平台限制）。
- 新增 `PhotoWriter` 行为单测（mock `PHPhotoLibrary` 不可行，改为协议层 mock 验证调用参数；真实写路径由 UI 测试覆盖）。
- 代码门禁：`deleteAssets` 只能出现在 `PhotoWriter.moveToRecentlyDeleted`；`setHidden` 只能出现在 `PhotoWriter.setHidden`。

**验收**：隐藏后系统相册「已隐藏」出现；删除后系统相册「最近删除」出现；App 内隐藏列表可见；批量删除在副本关闭时不产生副本；滑动 20 张只提交 1 次；无任何"永久删除"入口。

### D13 · 多选模式下无法滚动相册

**根因**：`LibraryViewController.swift:192-197` 创建了 `selectionPan` 并加到 `collectionView`；`enterSelectionMode`（213-225）把它 `isEnabled = true`。它和 `UICollectionView` 自带的 `panGestureRecognizer` 竞争同一个单指拖动，导致滚动被框选吃掉；且 `onSelectionPan` 没有 `gestureRecognizerShouldBegin` / 同时识别规则。

**修复策略（对齐系统相册）**：

- **删除常驻的 `selectionPan`**。
- 用 `UILongPressGestureRecognizer(minimumPressDuration: 0.28, allowableMovement: 10)` 驱动框选：
  - `.began`：如果不在多选，进入多选并选中该 cell；记录 anchor。
  - `.changed`：手指移动超过 10pt 才进入"框选模式"；此时才 `collectionView.isScrollEnabled = false`，显示 `selectionOverlay`，按矩形与 `layoutAttributesForElements(in:)` 选中。
  - 边缘自动滚动：`CADisplayLink` 或 1/60 `Timer`，当手指距顶部/底部 < 60pt 时以 8–12pt/帧滚动，并持续更新框选。
  - `.ended/.cancelled`：隐藏 overlay，恢复 `isScrollEnabled = true`。
- 普通单指快速滑动不会触发长按（`allowableMovement` 内），因此**正常滚动完全不受影响**。
- 框选只做"加选"；已选中的 cell 再次划过不取消（与系统一致）。
- 多选模式下双指捏合仍可改列数（Phase 7 验证）。

**验收**：多选模式下上滑/下滑能滚动；长按后拖动出现矩形并选中经过的 cell；拖到边缘自动滚动；松手后恢复滚动。

### D14 · 加入缩小/放大手势改变相册视图

**根因**：`LibraryViewController` 没有任何捏合手势；只有 `AppearanceSettingsView` 的 Stepper 改列数。

**修复策略**：

- 在 `LibraryViewController.collectionView` 加 `UIPinchGestureRecognizer`，`delegate` 允许与滚动同时识别（双指 vs 单指）。

- 提示：首次捏合后 Toast「双指捏合可调整列数」仅一次。

**验收**：双指张开 3→4/5 列、捏合 3→2 列；松手后列数持久化；重进 App 保持；锚点照片不跳走；设置页 Stepper 与手势结果一致。

### D16 · 会话式无感整理（暂存删除 / 暂存隐藏 / 智能补位）

> 本节是 2026-11-03 补充需求的核心，优先级高于 D03/D04 的旧描述；D03/D04 的"移除 App 确认"仍然有效，但真正解决"每张都弹"的是本节。

**目标**：上下滑操作期间**不做任何 PhotoKit 写操作**，只做本地队列 + 乐观 UI + 预取补位。删除在会话结束统一提交一次；隐藏按队列批量提交。用户连续滑 100 张，不应出现 100 次系统弹窗，也不应每张等待一次 PhotoKit。

**1. 核心模型（PhotoDeskCore，纯逻辑 + XCTest）**

```swift
public enum PendingKind: String, Codable { case delete, hide }

public struct PendingEntry: Codable, Hashable, Identifiable {
    public let assetID: String
    public let kind: PendingKind
    public let markedAt: Date
    public let originIndex: Int
    public var id: String { "\(kind.rawValue):\(assetID)" }
}

public struct ReviewSession: Codable, Equatable {
    public private(set) var entries: [PendingEntry]
    public var pendingDeleteIDs: [String] { ... }   // 保持入队顺序
    public var pendingHideIDs: [String] { ... }
    public mutating func markDelete(_ id: String, originIndex: Int, at: Date)
    public mutating func markHide(_ id: String, originIndex: Int, at: Date)
    public mutating func unmark(_ id: String, kind: PendingKind)
    public mutating func removeCommitted(_ ids: [String], kind: PendingKind)
    public var isEmpty: Bool
}

public enum VerticalEdge: String, Codable { case top, bottom }

public struct ReplacementPlan: Equatable {
    public let nextIndex: Int?
    public let entryEdge: VerticalEdge?
    public let shouldClose: Bool
}

public enum ReplacementPlanner {
    /// 纯函数：不依赖 UIKit；所有边界条件用 XCTest 覆盖
    public static func plan(currentIndex: Int,
                            countAfterRemoval: Int,
                            exitEdge: VerticalEdge?,
                            hasNext: Bool,
                            hasPrevious: Bool) -> ReplacementPlan
}
```

- `ReviewSession` 只存 assetID / kind / originIndex / 时间，不存图片、不存 `PHAsset`。
- `ReplacementPlanner` 不依赖 UIKit；`ViewerViewController` 只把 `VerticalEdge` 映射为 `CATransitionSubtype`/transform。
- 新增 `PhotoDeskCore/ReviewSession.swift`、`ReplacementPlanner.swift`、`BatchCommitPlanner.swift` 及对应测试。

**2. 持久化与控制器（App 层）**

- 新增 `PendingActionStore`（`PhotoDesk/Core/Support/PendingActionStore.swift`）：
  - 文件：`Application Support/PendingActions/session-v1.json`；原子写；`schemaVersion`。
  - 启动加载；文件损坏时重命名为 `session-v1.corrupt-<timestamp>.json` 并从空队列开始，不能 crash。
  - 队列上限 10,000 条；超过时拒绝继续入队并提示先提交，避免无界内存。
  - **不要给 Core Data 加实体**（现有程序化模型未启用自动迁移）。
- 新增 `ReviewSessionController`（`@MainActor`，ObservableObject）：
  - `session`、`pendingDeleteCount`、`pendingHideCount`、`isCommitting`、`commitProgress`。
  - `enqueueDelete(id:originIndex:)`、`enqueueHide(id:originIndex:)`、`undoPending(id:kind:)`。
  - `commitDeletes()` / `commitHides()` / `commitAll()`。
  - `flushHidesIfNeeded(reason:)`：进入 Vault、离开整理会话、App 进后台时调用。
  - 所有入队同步完成（内存），磁盘写入 0.2 秒 debounce；App 进后台/退出前强制 flush 到磁盘。
- 新增 `SessionReviewView`（SwiftUI sheet）：
  - 顶部「待删除 N · 待隐藏 M」；
  - 懒加载缩略图网格（`ImagePipeline`，200×200）；每张可「恢复」；
  - 按钮「继续整理」「全部移到最近删除」「全部隐藏」「关闭」；
  - 「全部移到最近删除」是唯一的删除提交入口；点击后显示进度，系统确认只出现一次。
- 新增 `SessionBadgeView`：照片库/查看器顶部显示待处理数量，点击打开 review。

**3. 交互流程（全程无感）**

1. 用户上滑/下滑触发删除或隐藏。
2. `ViewerViewModel` 立即：
   - `session.enqueueDelete(id, originIndex: currentIndex)` 或 `enqueueHide`；
   - 从当前 `items` 移除该 id；
   - 计算 `ReplacementPlan`；
   - 返回 `.staged(plan, toastText)`，**不 await PhotoKit**。
3. `ViewerViewController` 立即播放飞出动画；下一张按 plan 从顶部/底部补位；Toast「已标记待删除 · 撤销」/「已加入待隐藏 · 撤销」。
4. 顶部计数 +1；用户可继续滑，不中断。
5. 列表滑完或用户点「完成整理」→ `SessionReviewView`；用户可恢复任意项。
6. 用户点「全部移到最近删除」→ `commitDeletes()` → **一次**系统确认 → 成功后清空队列并 Toast「已移到系统「最近删除」N 张」。
7. 用户点「全部隐藏」→ `commitHides()` → 批量 `isHidden=true`；通常无系统确认；成功后清空队列。
8. 用户直接关闭 App/杀进程：队列已持久化；下次启动恢复计数与 review，不自动提交、不自动弹系统框。

**4. 智能补位策略（ReplacementPlanner）**

设当前删除项原 index = `i`，删除后数组长度为 `n`：

| 场景 | nextIndex | 补位进入边 | 说明 |
|---|---|---|---|
| 上滑删除/隐藏，后面还有 | `i`（原 i+1） | **bottom** | 卡片向上飞出，下一张从底部顶上来 |
| 下滑删除/隐藏，后面还有 | `i`（原 i+1） | **top** | 卡片向下飞出，下一张从顶部压下来 |
| 已是最后一张，回退上一张 | `i-1` | 与飞出边**相同**（上滑→top，下滑→bottom） | 到末尾时反向补位，像"回卷" |
| 工具栏/无手势删除 | `i` 或 `i-1` | **bottom**（默认前进） | 无手势方向时用默认方向 |
| 删除后列表为空 | `nil` | `nil` | 关闭查看器，回到网格 |
| 连续快速操作 | 动画串行队列 | 同上 | 正在补位时锁定手势，最多 1 个动画；后续操作排队合并 |
| 横向翻页 | 不补位 | 无 | 横向只浏览，不触发动作 |

- 补位动画：当前 cell 飞出 → `collectionView.performBatchUpdates` 删除 cell → 更新 `currentIndex` → 用 `snapshotView` 把下一张从 `entryEdge` 以 0.96→1.0 缩放/8–16pt 位移进入；动画结束解锁手势。
- 若下一张图片尚未解码：先显示已缓存的缩略图/模糊占位，图片到达后交叉淡入；**不能显示上一张**。
- 网格补位：`applySnapshot(animatingDifferences: true)`；删除当前 section 最后一项时移除 section header；如果当前可见区被删空，`scrollToItem` 到下一个可见项，避免空白。
- 预取：查看器 prefetch 当前 index 后 3 张 + 前 1 张；`ImagePipeline` 预热；连续滑动时保持 55 FPS。

**5. 提交策略（BatchCommitCoordinator）**

- 删除：
  1. 按 500 个 id 一批 `PHAsset.fetchAssets(withLocalIdentifiers:)` 解析（只解析，不删除）；缺失的 id 标记为 alreadyGone。
  2. 若 `trash.safetyCopyEnabled == true`：逐项 `trashBin.storeCopy`，进度显示；iCloud-only 无法下载的项**跳过并保留在队列**，不能删除无副本项。
  3. 所有可删除 id 放入**一次** `PHPhotoLibrary.performChanges { PHAssetChangeRequest.deleteAssets(assets) }`；系统确认一次。
  4. 成功：`removeCommitted`、清空对应队列、刷新网格/Vault；失败/用户取消：保留队列，Toast 说明。
  5. 单次提交上限 5,000 张；超过则按 5,000 分批（每批一次系统确认，仍是每 5,000 一次，不是每张）。
- 隐藏：
  1. 一次 `performChanges` 批量 `PHAssetChangeRequest(for:).isHidden = true`；
  2. 成功清空 `pendingHide`；失败保留并恢复本地 item；
  3. 进入 Vault 前先 `flushHidesIfNeeded`，保证 Vault 能看到刚隐藏的照片。
- 幂等：提交前记录 `commitToken`；若 App 在 `performChanges` 成功后、清空队列前崩溃，下次启动按 assetID 检查：已不在库中 → 视为成功并清除；仍在库中 → 保留队列。
- 撤销：
  - 提交前：从队列移除即可，零 PhotoKit 写；
  - 提交后：仅当 `TrashBin` 有副本时提供 App 内撤销；否则提示「已移到系统「最近删除」，请在系统相册 30 天内恢复」。
- 代码门禁：`deleteAssets` 只允许在 `PhotoWriter.moveToRecentlyDeleted` 内；`setHidden` 只允许在 `PhotoWriter.setHidden` 内；`ReviewSessionController` 只能调用这两个协议方法。

**6. 与现有功能的关系**

- D01/D02：查看器仍按 assetID 定位；删除/隐藏改为本地移除 + `ReplacementPlan`，不再 await 写库，彻底消除"删除目标漂移"。

## 2. 目标架构

### 2.1 核心模型

```
LibraryQuery ──► LibraryFeed（PhotoKit，分批 500）
     │                    │
     │                    ▼
     │            LibrarySnapshot（allItems / filteredItems / sections）
     │                    │
     ▼                    ▼
SelectionState ◄── LibraryViewController（网格 / 选择 / 滚动位置）
     │
     ▼
ViewerContext(items: filteredItems, startItemID: clickedID)
     │
     ▼
ReviewSession（pendingDelete / pendingHide）
     │
     ▼
BatchCommitCoordinator（deleteAssets 一次 / setHidden 一次）
```

**原则**：

- **单一事实来源**：主网格、全选、查看器、位置记忆都使用同一份 `filteredItems`；不再让 `SearchView` 自己拿一份 `itemsSnapshot`。
- **按 assetID 不按 index**：跨层传递一律用 `PhotoItem.id`；index 只在当前集合视图内部使用。
- **滑动只入队**：删除/隐藏先写 `ReviewSession`，本地移除并补位；PhotoKit 写操作只在 `BatchCommitCoordinator` 发生。
- **纯逻辑下沉 `PhotoDeskCore`**：新增 `GeoFilter`、`SelectionPolicy`、`StorageMath`、`ReviewSession`、`ReplacementPlanner`、`BatchCommitPlanner`；`DateSectionizer` 已有，本次补 `ascending` 参数。新增的位置聚类、选择状态、统计聚合、会话队列、补位策略必须有 XCTest。
- **App 层只做适配**：`CLLocation` → `GeoPoint`、`PHAsset` → `PhotoItem`、`UIAlertController` 呈现、`UICollectionView` 补位动画等。

### 2.2 `LibraryViewModel` 新状态

```swift
@MainActor
final class LibraryViewModel: ObservableObject {
    @Published private(set) var query: LibraryQuery
    @Published private(set) var allItems: [PhotoItem] = []       // 完整索引（分批加载，含 pending）
    @Published private(set) var visibleItems: [PhotoItem] = []   // 排除 pendingDelete/pendingHide
    @Published private(set) var filteredItems: [PhotoItem] = []  // 当前筛选结果（基于 visibleItems）
    @Published private(set) var sections: [MonthSection] = []
    @Published private(set) var itemsBySection: [[PhotoItem]] = []
    @Published private(set) var indexProgress: (loaded: Int, total: Int) = (0, 0)
    @Published private(set) var isIndexing = false
    @Published private(set) var pendingDeleteIDs: Set<String> = []
    @Published private(set) var pendingHideIDs: Set<String> = []
    @Published private(set) var viewState: ViewState

    func start() async
    func setScope(_ scope: PhotoScope) async
    func setFilter(_ filter: SearchPredicate) async
    func setSort(ascending: Bool) async
    func ensureIndexComplete() async
    func applyPendingChanges(_ session: ReviewSession) async
    func itemsSnapshotForViewer() -> [PhotoItem]   // = filteredItems
}
```

**加载策略**：

1. `prepare(scope:)` 拿总数；先取前 500 张 → `viewState = .ready`，首屏尽快出现。
2. 后台继续按 500/批取剩余；每批合并到 `allItems`，每 2,000 条或 0.3 秒合并一次 `rebuildSections`，避免 10,000 次 diff。
3. 筛选/全选/位置记忆都基于 `allItems`；筛选计算在 `Task.detached`，主线程只应用结果。`filteredItems` 之前先排除 `ReviewSession` 的 pending 项：待删除/待隐藏在网格上立即消失，只在 `SessionReviewView` 中可恢复。
4. 若 `total > 30,000`：启用降级模式——日期/媒体/收藏用 `PHFetchOptions` 谓词下推，位置筛选仅对已加载范围生效并明确提示；避免内存不可控。
5. 变更 observer 应用到 `allItems` 后 **重新应用当前 filter 与 pending 过滤**，再推快照；不允许把"筛选结果"和"原始结果"混在一个数组里。
6. `ReviewSessionController` 每次 `enqueue/unmark/commit` 后调用 `applyPendingChanges`；网格顶部显示「待删除 N / 待隐藏 M」入口。

### 2.3 `SelectionState`

- 进入多选时 `scope = Set(filteredItems.map(\.id))`。
- 筛选/scope 变化：`selected = selected.intersection(newScope)`；若为空可自动退出。
- `selectAll()`：`selected = scope`；`deselectAll()`；`invert()`。
- 全选是 O(n) 集合操作，不逐 cell 遍历；UI 只刷新可见 cell + 状态栏计数。
- 选择状态不持久化（离开页面即清空）；"上次整理位置"与选择无关。

### 2.4 `ViewerContext` 与动作策略

```swift
struct ViewerContext: Identifiable {
    let id = UUID()
    let items: [PhotoItem]          // 当前筛选结果
    let startItemID: String
    let queryKey: String
}
```

| 动作 | 写库 | 本地效果 | 自动前进 |
|---|---|---|---|
| favorite / unfavorite | `setFavorite`（乐观更新，后台写） | 更新 item 的 isFavorite | 否 |
| toggleFavorite | 同上 | 同上 | 否 |
| hide | `ReviewSession.enqueueHide`（不立即写库） | **从 viewer items 移除**，Vault 合并 pending | 是（ReplacementPlan） |
| unhide | `setHidden(false)` 立即写 | 从隐藏列表移除 | 是（隐藏页） |
| moveToRecentlyDeleted | `ReviewSession.enqueueDelete`（不立即写库） | **从 viewer items 移除** | 是（ReplacementPlan） |
| addToAlbum | `add(ids:toAlbum:)` | 无 | 否 |
| share / showInfo / rotate | 无 / 打开编辑器 | 无 | 否 |
| dismiss | 无 | 关闭 | — |

**未实现动作的处置**：`addToAlbum`、`share`、`showInfo`、`rotate` 全部接入；不允许再出现「该动作将在后续里程碑开放」。

## 7. 平台限制与风险

| 风险 | 影响 | 处置 |
|---|---|---|
| **删除系统确认弹窗无法去除** | 每张删除都会弹，无法连续操作 | **会话暂存 + 一次批量提交**：滑动 0 弹窗，提交 1 次；不要用私有 API |
| **第三方无法做到"零弹窗 + 真删除"** | 用户期望可能落空 | 明确三条路：批量 1 次 / 仅隐藏 / 私有 API（禁止）；产品需接受其一 |
| **pending 队列持久化失败/损坏** | 丢待删除记录 | 原子写 + 损坏备份 + 启动恢复 + 队列上限 10,000 |
| **系统确认被用户取消** | 队列保留但用户以为已删 | 明确 Toast「系统未允许删除，N 张仍在待删除」；review 计数不丢 |
| **iCloud-only 副本失败** | 无法落 TrashBin | 该项跳过并保留队列，不能删除无副本项；提示先下载 |
| **IPA 未签名/签名失败** | 用户装不上 | CI 校验未签名 + SHA256 + `docs/12`；签名问题由用户侧排查，不伪装真机验证 |
| **iOS 16+ 系统「已隐藏」相册在 Photos UI 默认锁定** | 用户可能以为隐藏失败；受限授权下第三方 App 也读不到隐藏资源 | 完全授权下用 `includeHiddenAssets = true` 读取；受限授权提示去 设置→照片 允许完全访问；真机验证 |
| **模拟器无 Face ID** | 无法自动验证生物识别 | 单测 mock + UI 测试 bypass + 真机清单 |
| **iOS 无公开 API 枚举「最近删除」** | App 内不能列出已删照片 | 保持说明页 + `photos-redirect://`；不伪造列表 |
| **iCloud-only 资源大小未知** | 统计偏小 | 显示"未知大小 N 项"；不阻塞 |
| **PhotoKit observer 索引漂移** | 删除/插入后错位 | 每次变更用 `fetchResultAfterChanges` 重建索引；UI 用 id 不用 index |
| **全量索引内存** | 大库内存上涨 | 30,000 张以上降级为谓词下推；分批 + 合并快照 |
| **CI 时长/配额** | 多轮失败 | UI 测试用 mock + 缩小数据集；单轮只跑必要测试；最多 10 轮修复 |
| **iOS 15 API 黑名单** | 编译失败 | `NavigationStack`/`PhotosPicker`/`ShareLink`/`Charts`/`@Observable` 禁用；新代码逐行检查 |
| **免费签名 7 天** | 真机验证窗口短 | 验收集中在 CI；真机清单一次跑完 |
